# 模组简介

《植物大战僵尸杂交版》的托管 C# Mod，把游戏各界面的背景音乐换成玩家自己放的歌。
**模组包内不携带任何音频文件** ，模组运行时将从模组指定的目录下读取音频文件，切换歌曲与新增歌曲无需重启游戏，提示需要重启均为游戏设计所致。

- 适用游戏版本：《植物大战僵尸杂交版》`0.30.0.0`
- 引擎版本：Godot `4.7.0`（.NET 版）
- .NET 目标框架 `net9.0`，所需 SDK `9.0` 及以上
- 模组版本：`1.2.4`
- 模组作者：百合小希

**关于开发方式**：本模组是在 Qwen3.8 Flash 的协助下开发的，本模组所有内容均由 AI 参与制作与审阅。
仓库就是完整源码，如有疑问，请联系我，虚心听劝。

## 这个模组能做什么

- **界面音乐替换**：主菜单、商店弹窗、选关、图鉴各一个下拉，在游戏的「Mod 管理 → 音乐盒 → 配置」里选，每组第一项是总开关，关掉整组回到游戏原声。
- **按文件名成曲**：`存档目录\Seeleyuwo\rez\BGM\` 里（含任意深度的子文件夹）每一个音频文件就是一首可选曲目，曲名 = 文件名。
- **战斗 BGM 覆盖**：文件名正好是游戏里某首战斗背景音乐的曲名（共 13 首）时，自动替换那一首，不用在面板里选。
- **换文件不用重启**：模组每秒核对目录指纹，变了当场重载，正在播的界面也会换曲。
- **续播**：从载入界面进主菜单、选关、图鉴时不再从头重播，接着刚才的位置播。
- **格式预检**：游戏读不了的歌（超 64MB、24-bit FLAC 等）不会出现在下拉里，日志会点名是哪一首、为什么、该转成什么格式；格式按**文件头**认，所以"文件名是 .mp3、里面其实是 FLAC"这种挂错名的歌也能正常播。

本模组只管背景音乐：**战斗报幕音和游戏音效一律保持原版**，不读、也不接管任何音效目录。

## 怎么用

1. 把音频丢进 `存档目录\Seeleyuwo\rez\BGM\`，即
   `%APPDATA%\Godot\app_userdata\植物大战僵尸杂交版\Seeleyuwo\rez\BGM\`，可以自己建子文件夹分类。
2. 选项 → Mod 管理 → 音乐盒 → 配置，四个界面各选一首。
3. 能读的格式：wav / ogg / mp3 / **16-bit 立体声** FLAC，单个不超过 64MB。24-bit FLAC、5.1 声道、wma / m4a / aac 这类游戏没有解码器的格式都读不了 —— 转成 ogg 或 mp3 最省事（`ffmpeg -i 输入 -vn -ac 2 -c:a libmp3lame -q:a 0 输出.mp3`）。
4. 新歌**播放**不用重启，但要出现在下拉里得重启一次游戏（下拉选项存在安装包内，模组重启时会把声明重写成目录实际扫到的曲目）。

## 仓库结构

```
mod.json                  模组清单：settings 面板声明、playInstructions、资源与运行时入口
Scripts/MusicBoxEntry.cs  运行时代码主体：面板、音频扫描、场景与对话钩子、包内声明回写
Scripts/MusicBoxUpdate.cs 同一个类的另一半（partial）：更新源、启动时那一次请求与重试、严格 semver 比较、上报统一提醒
changelog.txt             更新记录的唯一来源，模组会把它回写进「关于」页
LICENSE                   MIT 许可全文
build.py                  构建一条龙：编译 → 校验 → 打包 → 核对（见「构建与打包」）
.build/                   构建 / 校验 / 打包工具（见「构建与打包」）
```

`.build/Directory.Build.props` 是宿主程序集引用的唯一入口：按 `PVZHostDir`（或环境变量 `PVZHOSTDIR`）
找那两份宿主程序集，缺了就带着「缺什么」停下。仓库里不写任何作者本机的路径。

## 构建与打包

需要 **.NET SDK**，版本要求见开头「适配版本」那一节：三个工程的目标框架都是它填的那个，同系列更高的小版本也能编，比它低的编不了。
需要 **Python 3**（跑构建脚本，只用标准库，不需要 `pip install` 任何东西）。
三个 csproj 都不引第三方 NuGet 包，但首次构建仍要联网从 nuget.org 取那个目标框架的引用包，之后可以离线重复构建。

外加**你自己准备的宿主程序集**：游戏发行时附带的两份托管 DLL（游戏本体的编译产物，加上 Godot .NET 的脚本程序集）。
本仓库不带它们，也不记录任何作者本机的路径 —— 它们是游戏的产物，随游戏分发，版权不在本仓库。

模组是托管 C# 插件，编译期必须拿到含宿主类型定义的程序集才能通过编译；这份引用只用于编译，
不会被打进 `.pmod`，运行时直接用游戏里已经加载的那一份。第三方 mod 也都是这个形状：解包后只有
清单和一份托管 DLL，DLL 引用的同样是这两份宿主程序集。

怎么把这个目录告诉构建，有三种写法，任选其一：环境变量 `PVZHOSTDIR=<目录>`（推荐，设一次长期有效，`build.py` 和三个离线工具都读它）、
`python build.py --host-dir <目录>`、或给 `dotnet build` 加 `-p:PVZHostDir=<目录>`。
它要指向的是**那两份宿主程序集所在的那个文件夹**：装好游戏后一般在 `<游戏安装目录>\data_PlantsVsZombies_*\` 里，
`PlantsVsZombies.dll` 与 `GodotSharp.dll` 同时出现在某个目录下，指的就是那个目录；文件夹名里的平台和架构部分会随游戏版本变，
拿不准就在安装目录里搜这两个文件名。没指定、或那个目录凑不齐时，构建会带着「缺什么」直接停下，不会去猜路径。

一条龙是仓库根目录的 `build.py`，它按顺序跑完编译 → 校验 → 打包 → 核对包内容，任何一步失败就停在那里：

```bash
python build.py --host-dir "<含那两份宿主程序集的目录>"   # 已设好 PVZHOSTDIR 的话不用这个参数；相对路径按仓库根目录算
python build.py --install          # 出包并装进存档 Mods\（默认不装，游戏读到的还是旧包）
python build.py --probe "<BGM 目录>"   # 额外跑一遍音频预检，可重复指定多个目录
```

**版本号一律严格 semver**（SemVer 2.0）：正式版写三段（`1.2.3`、`1.3.0`），内测照预发布标记分三档——
`1.3.0-alpha.1`（还在试方向）、`1.3.0-beta.2`（功能齐了、等验证）、`1.3.0-rc.1`（没新问题就当正式版发）。
它由定版的人手写进 `mod.json` 的 `version`，打包一个字节都不改它；写成四段（`1.2.2.6`）或带上构建号都会被打包直接拦下。
定新版要一起改的只有三处：`version`、「关于」页那句 `音乐盒 v<版本号>`、以及 `changelog.txt` 里新加的那一段
（改完跑一次 `python .build/seed.py`，把公告正文同步进 `mod.json`）。
**构建号已经取消**：同一个版反复出包就是覆盖同一个包名（正式包就叫 `MusicBox-<版本号>.pmod`，不带 ID 哈希那串后缀——
防撞靠 `mod.json` 里的 `id`，文件名那八个字符对玩家没有意义），
换版本后旧包名会留在 `dist\` 和存档 `Mods\` 里，所以打包会把同前缀的旧包删掉——
游戏见到两个相同 ID 的包会判「存在重复的已安装 Mod ID」，整批不加载。

`build.py` 全程不写仓库里的任何文件，所以它本身就能当流程自检用：克隆下来直接跑一遍，闸门全过就说明这台机器能构建。

默认只在 `dist/` 里出包，不碰存档目录；构建缓存（TEMP / NuGet / dotnet CLI）也都收进 `.build/` 里，不污染系统临时目录。
想只跑其中一步，或者想知道每一步分别在干什么，照下面抄（都在仓库根目录执行）：

```bash
export TEMP="$PWD/.build/TEMP" TMP="$PWD/.build/TEMP" TMPDIR="$PWD/.build/TEMP" \
       DOTNET_CLI_HOME="$PWD/.build/tmp" NUGET_PACKAGES="$PWD/.build/tmp/nuget" \
       PVZHOSTDIR="<含那两份宿主程序集的目录>"

# 1. 编译运行时 DLL（引用宿主程序集，但不把它们拷进输出目录）
dotnet build .build/ModAssembly.csproj -c Release -o .build/bin/Release --nologo -p:UseSharedCompilation=false

# 2. 离线校验 mod.json 的 settings 声明（反射宿主面板，不用开游戏；读 PVZHOSTDIR）
dotnet run --project .build/validate -c Release -- mod.json

# 3. 离线跑一遍音频预检，确认音乐目录里每首歌游戏能不能读（要给出目录）
dotnet run --project .build/probe -c Release -- "<BGM 目录>" [额外目录...]

# 4. 打包（只出包；不带 --no-install 会顺手装进存档 Mods\）
python .build/package.py "$PWD" --no-install

# 5. 核对包内容
python .build/verify.py

# 6. 版本号比较的真值表（直接从 MusicBoxUpdate.cs 抽出那段 semver 实现来跑，不引用游戏）
python .build/semver_probe.py
```

PowerShell 下这些环境变量这样设（上面那段是 bash 写法，`build.py` 本身两个 shell 都能跑）：

```powershell
$env:TEMP = $env:TMP = $env:TMPDIR = "$PWD\.build\TEMP"
$env:DOTNET_CLI_HOME = "$PWD\.build\tmp"
$env:NUGET_PACKAGES = "$PWD\.build\tmp\nuget"
$env:PVZHOSTDIR = "<含那两份宿主程序集的目录>"
```

`python .build/verify.py` 把包内容当成一份清单核对（id/名称/设置项/更新记录一致性、
关键实现是否真在 DLL 里），结果写到 `.build/TEMP/verify.txt`。
`.build/package.py` 的安装步骤按 `%APPDATA%\Godot\app_userdata\植物大战僵尸杂交版\Mods\` 定位存档目录，
那是游戏自己的用户数据目录；不是这台机器的路径，换机不用改，只想出包就一直带 `--no-install`。

## 已知宿主限制（改动前值得先看一眼）

- 游戏读外部音频时**只按传入的扩展名选解码方式**，不看文件内容；单个文件上限 64MB，FLAC 还要求 8/16-bit、单声道或立体声、解码后不超过 128MB。模组因此自己按文件头认格式，挂错名的歌也能播，读不了的进下拉前就被拦下。
- 游戏的 Mod 配置面板只有开关、数值、文本、下拉这类普通项，没有按钮，所以面板里做不出「刷新」这类交互；面板还要求包体和启动时登记的指纹一致，模组每次启动把下拉选项重写成目录实际扫到的曲目后，本局会提示「正在使用旧版本，重启并应用」——这是预期行为。
- 从载入界面进主菜单（选关、图鉴同理）时，游戏会把同一首音乐从头重放一遍，这个行为模组拦不住，只能在下一帧把播放位置按回刚才的地方，实现续播。
- 游戏导出时裁剪了部分 .NET 运行库：标准 HTTP 客户端不能直接用，联网检查更新走的是宿主提供的请求通道；个别字符串拆分写法会绑到被裁剪的重载上，低层的字节解析也都是手写避开的。
- 更新检测已同步游戏官方的统一更新接口：发现新版由游戏汇总提醒，本模组不自建弹窗。

## 更新源

发新版就是**发一个 GitHub Release**：模组每次启动查
`https://api.github.com/repos/NaiyxYin/PVZHE_MusicBox/releases/latest`，把返回里的 `tag_name` 当最新模组版本、
`html_url`（也就是 Release 页）当下载页。仓库里不再有 `update.txt`，线上没有需要单独维护的更新文件。

- tag 写**严格 semver**：正式版就 `1.2.3`，内测就 `1.2.3-beta.1`（带 `v` 前缀也行，读的时候会去掉）。不符合规范的 tag（比如写成四段 `1.2.3.0`）模组认出来会**只记一条日志、不作提醒**，因为比不了大小就不该把玩家引过去。
- 比较照 semver 规范：`1.3.0-alpha.1 < 1.3.0-beta.2 < 1.3.0-beta.10 < 1.3.0-rc.1 < 1.3.0`；`+构建元数据`按规范不比，tag 也只写版本本身（构建号已取消），所以不会有「每次打包都提示有更新」的问题。
- 内测 Release 要在 GitHub 上勾 **pre-release**：`/releases/latest` 只返回「最新的非草稿、非预发布」那一条，所以内测包不会推给玩家，玩家只会收到正式版的提醒。装了内测包的人升到正式版时照样会收到提醒（正式版大于同号的任何预发布）。
- `.pmod` 传成这个 Release 的**附件**（`dist/*.pmod`）；玩家点提醒里的「打开更新页面」就落到 Release 页，附件和更新说明都在那儿。内测包不用建附件以外的渠道，把 Release 页链接直接发给测试的人就行。
- 发现新版就交给宿主的统一更新提醒：游戏把所有 Mod 的更新汇总成一份，列出「模组名 · 当前版本 → 新版本」和一个「打开更新页面」按钮，模组自己不弹窗。
- 任何失败（连不上、404、回来的不是 JSON）都**只写一条日志，绝不打扰玩家**，失败会隔 3 秒静默重试一轮。
- 游戏只在**进主菜单后的 2 秒内**收集各 Mod 上报的更新，用这份收集结果决定要不要自动弹提醒；晚于 2 秒上报的不会自动弹，但仍会留在「更新列表」里可以手动打开。网慢就是这个表现，跟"没建正式版 Release"的静默不同，日志能分清是哪种。
- 还没有正式版 Release（全都还是草稿或预发布）时这个地址返回 404，等同「已最新」；仓库是 private 时同样 404，转 public 后自动恢复。

地址写在 `Scripts/MusicBoxUpdate.cs` 的 `UpdateFeedUrl` 里，仓库搬家 / 改名时要一起改；
GitHub API 不给 `User-Agent` 会直接 403，所以同处的 `UpdateFeedHeaders` 也得留着。
`python .build/verify.py` 会核对这几件事：`version` 是严格 semver 且不带 `+构建元数据`、「关于」页那句正好是 `v<版本>`、
包名正好是 `MusicBox-<版本>.pmod` 且没混进 ID 哈希后缀、更新源地址里没有占位（例如还没填的 `OWNER`）、
地址确实是 `/releases/latest`、请求带 `User-Agent`、仓库里没有残留的 `update.txt`、以及 semver 那套实现真的编进了 DLL。

实机日志在 `存档目录\logs\godot.log`，正常启动会有一行 `[Mod:MusicBox] 运行入口已加载 v<版本>`；没有这行说明跑的还是旧包。
